# 테스트 코드 규칙

## 패키지 구조

- 운영 코드의 단위 테스트는 `src/test/java`에서 운영 코드와 동일한 패키지에 둔다.
- 여러 모듈, HTTP 보안, 마이그레이션, 외부 저장소처럼 실행 환경을 함께 검증하는 테스트는 `integration/<capability>`에 둔다.
- 재사용 가능한 테스트 데이터와 시나리오는 `fixture/<capability>`에 둔다. 운영 코드의 DTO, Entity, Service에 테스트 전용 생성 책임을 추가하지 않는다.
- 아키텍처 규칙 검증은 `architecture`에 둔다.

## 명명과 시나리오

- 테스트 클래스는 검증 대상을 기준으로 `*Test`로 끝낸다. 통합 여부는 패키지 위치로 구분한다.
- 테스트 메서드는 lower camel case의 행동 중심 문장으로 작성하고, 조건과 기대 결과가 드러나야 한다.
- 하나의 테스트는 Given-When-Then 순서로 읽힌다. 준비 코드가 짧으면 별도 주석 없이 문장형 메서드명으로 의도를 표현하고, 준비·실행·검증이 길어질 때만 `given`, `when`, `then` 주석으로 구획한다.

## 검증 범위

- 성공, 대표 실패, 경계 조건을 각각 검토한다. HTTP 테스트는 상태 코드와 오류 계약을 함께 검증한다.
- 단위 테스트는 Mockito 등으로 직접 의존성을 대체하고 Spring Context를 올리지 않는다.
- 통합 테스트는 실제 빈 연결, 보안 필터, 트랜잭션 또는 저장소 계약을 검증할 때만 사용한다.
- PostgreSQL 방언, Flyway, 잠금, 동시성처럼 H2로 재현할 수 없는 계약은 Testcontainers PostgreSQL을 사용한다.
- S3, FCM, OAuth, 이메일 등 외부 시스템은 단위·통합 테스트에서 대체 구현 또는 mock으로 격리한다. 실제 외부 연동은 별도 계약 또는 수동 검증 범위로 둔다.

## 픽스처와 중복 테스트

- 픽스처는 의미 있는 기본값과 필요한 최소 변경 지점만 제공한다. 전역 만능 fixture나 무작위 시간·ID에 의존하는 기본값은 만들지 않는다.
- 테스트 내부에만 필요한 데이터는 해당 테스트의 private factory로 유지한다.
- 같은 행위를 검증하는 테스트는 하나로 합치되, 서로 다른 권한·오류 코드·트랜잭션·DB 방언을 검증하면 중복으로 제거하지 않는다.
- 테스트 삭제 전에는 대체 테스트가 동일한 성공·실패 조건을 검증하는지 확인한다.
