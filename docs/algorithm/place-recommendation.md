# 장소 추천 알고리즘 설계

## 1. 문서 목적

이 문서는 Pingdom Backend의 장소 추천 알고리즘을 정의한다.

이 알고리즘의 목적은 단순 인기순 정렬이 아니라 다음을 동시에 만족하는 것이다.

- 사용자 현재 위치와 문맥에 맞는 장소를 찾는다.
- 사용자 반응 이력을 기반으로 취향을 전파한다.
- 신규 장소가 영구적으로 묻히지 않도록 탐색 기회를 준다.
- 비슷한 장소만 반복 노출되지 않도록 다양성을 제어한다.

## 2. 설계 원칙

- 추천은 단일 점수식이 아니라 다단계 파이프라인으로 본다.
- 조회 성능과 설명 가능성을 동시에 고려한다.
- 현재 보유 데이터로 구현 가능한 범위부터 시작한다.
- 코드 구현 시 일반 장소 조회와 추천 조회의 책임을 분리한다.
- 추천 결과에는 추천 사유를 함께 반환할 수 있어야 한다.

## 3. 현재 활용 가능한 입력 신호

현재 스키마 기준으로 즉시 활용 가능한 신호는 다음과 같다.

| 신호 | 소스 | 의미 |
|---|---|---|
| 사용자 북마크 | `map_bookmark` | 강한 선호 |
| 사용자 좋아요 | `map_image_like` -> `map_image.map_place_id` | 중간 선호 |
| 장소 사진 수 | `map_place.photo_count` | 장소 활성도 |
| 장소 내 좋아요 총합 | `map_image.like_count` | 반응도 |
| 장소 최근 업로드 | `map_image.created_time` | 최신성 |
| 장소 좌표 | `map_place.location`, `latitude`, `longitude` | 거리 기반 후보 생성 |

현재 부족한 신호는 다음과 같다.

- 노출 수
- 클릭 수
- 체류 시간
- 장소 카테고리
- 리뷰 평점

따라서 1차 구현은 `위치 + 행동 그래프 + 탐색 보정` 중심으로 설계한다.

## 4. 알고리즘 전체 구조

추천은 다음 6단계로 처리한다.

1. 사용자 컨텍스트 해석
2. 후보군 생성
3. 사용자-장소 그래프 선호 전파
4. 품질 및 탐색 보정
5. 다양성 재정렬
6. 추천 사유 생성

즉, 최종 점수는 마지막 정렬 결과일 뿐이고 알고리즘 본체는 `후보 생성`과 `선호 전파`에 있다.

## 5. 1단계: 사용자 컨텍스트 해석

입력은 다음을 기준으로 한다.

```text
userId(optional)
latitude
longitude
radiusKm
limit
```

컨텍스트 해석 규칙은 다음과 같다.

- 로그인 사용자는 개인화 추천을 시도한다.
- 비로그인 사용자는 위치 기반 추천만 수행한다.
- 사용자 반응 이력이 부족하면 개인화 가중치를 낮춘다.
- 주변 후보가 적으면 반경을 순차적으로 확장한다.

반경 확장 정책 예시는 다음과 같다.

```text
5km -> 10km -> 20km
```

## 6. 2단계: 후보군 생성

후보군은 단일 소스로 만들지 않는다. 추천 품질을 위해 서로 다른 성격의 후보를 합친다.

### 6-1. Geo Candidate

- 현재 위치 반경 내 장소를 PostGIS 기준으로 추출한다.
- 기본 반경은 5km로 시작한다.
- 최대 후보 수는 100~200개로 제한한다.

역할:
- 사용자 현재 문맥을 강하게 반영한다.
- 추천 결과가 먼 지역으로 튀는 것을 막는다.

### 6-2. Personal Candidate

- 사용자가 북마크한 장소
- 사용자가 좋아요를 누른 게시글이 연결된 장소
- 사용자가 업로드한 게시글이 속한 장소

이 seed 장소들로부터 유사 장소를 확장한다.

역할:
- 사용자의 명시적/암묵적 취향을 반영한다.

### 6-3. Trend Candidate

최근 일정 기간 동안 다음 값이 빠르게 증가한 장소를 후보에 포함한다.

- 최근 업로드 수
- 최근 좋아요 수
- 최근 북마크 증가량

현재 북마크 증가량은 별도 집계가 필요하므로 1차 구현에서는 업로드/좋아요 중심으로 시작한다.

역할:
- 신선한 장소를 후보군에 끌어들인다.

## 7. 3단계: 사용자-장소 그래프 선호 전파

핵심 알고리즘은 `User-Place-Place Graph` 기반으로 설계한다.

### 7-1. 그래프 구성

노드는 다음 두 종류로 구성한다.

- `User`
- `Place`

엣지는 다음 규칙으로 구성한다.

#### 사용자-장소 엣지

- bookmark: 강한 선호
- like: 중간 선호
- upload: 약한 선호

예시 가중치:

```text
bookmark = 1.0
like = 0.6
upload = 0.3
```

#### 장소-장소 엣지

- 지리적으로 가까운 장소
- 같은 사용자들에게 함께 북마크된 장소
- 같은 사용자들에게 함께 좋아요된 장소

즉 장소 간 관계는 단순 거리뿐 아니라 행동 유사도도 포함해야 한다.

### 7-2. 장소-장소 유사도

장소 `i`, `j` 사이 유사도는 아래처럼 계산한다.

가중 합산 전에 각 구성 요소는 모두 `[0, 1]` 범위로 정규화한다고 가정한다. 그래야 특정 항목의 스케일이 전체 유사도를 과도하게 지배하지 않는다.

```text
sim(i, j) =
  0.40 * geoKernel(i, j) +
  0.35 * coBookmarkPMI(i, j) +
  0.15 * coLikeCosine(i, j) +
  0.10 * trendSimilarity(i, j)
```

각 항의 의미는 다음과 같다.

- `geoKernel`: 두 장소가 가까울수록 큰 값
- `coBookmarkPMI`: 같은 사용자들이 함께 저장한 경향
- `coLikeCosine`: 같은 사용자들의 반응 벡터 유사도
- `trendSimilarity`: 최근 성장 패턴 유사도

이 유사도는 사전 계산 또는 snapshot으로 관리하는 것이 바람직하다.

### 7-3. Personalized Random Walk with Restart

사용자의 seed 장소에서 시작해 선호를 인접 장소로 전파한다.

의사코드는 다음과 같다.

```text
seedScore(place) =
  1.0 if bookmarked
  0.6 if liked
  0.3 if uploaded

r0 = normalize(seedScore vector)
r = r0

repeat k times:
  r = (1 - alpha) * W * r + alpha * r0
```

- `W`: 장소-장소 전이 행렬
- `alpha`: seed 복귀 계수
- `k`: 반복 횟수

권장 초기값:

```text
alpha = 0.15
k = 10~20
```

이 방식의 장점은 다음과 같다.

- 사용자가 직접 반응하지 않은 장소까지 선호를 전파할 수 있다.
- 비슷한 장소를 단순 태그 없이도 찾을 수 있다.
- 설명 가능한 추천 사유를 만들기 쉽다.

## 8. 4단계: 품질 및 탐색 보정

그래프 점수만으로 정렬하면 신규 장소와 전역 인기 장소 사이 균형이 무너질 수 있다. 따라서 품질과 탐색 보정을 별도로 적용한다.

### 8-1. 품질 점수

품질 점수는 다음 신호를 안정화해서 계산한다.

- `photoCount`
- 장소 내 게시글 총 좋아요 수
- 최근 업로드 유무

단순 합산 대신 Bayesian smoothing을 사용한다.

예시:

```text
m > 0

quality(place) =
  (likeSum + m * globalLikeMean) / (photoCount + m)
```

의도:
- 표본이 작은 신규 장소의 과대평가를 막는다.
- 무조건 오래된 인기 장소만 상단에 고정되는 현상도 줄인다.

### 8-2. 탐색 보너스

추천 시스템은 이미 잘 알려진 장소만 계속 보여주면 학습이 멈춘다. 따라서 제한적 탐색 슬롯을 둔다.

```text
explorationBonus(place) =
  sqrt(log(totalExposure + 1) / (placeExposure + 1))
```

현재 스키마에는 exposure 로그가 없으므로 초기 단계에서는 대체 신호를 사용한다.

- 임시 대체안: 최근 추천 노출 배치 로그 도입 전까지 `신규 장소 등록 시간` 기반 보너스 사용
- 정식안: 추천 노출 로그 테이블 추가 후 UCB 방식 적용

## 9. 5단계: 다양성 재정렬

상위 추천 결과가 모두 비슷한 동네나 같은 유형의 장소로 채워지면 체감 품질이 낮아진다. 따라서 최종 단계에서 `MMR` 기반 재정렬을 적용한다.

```text
MMR(candidate) =
  lambda * relevance(candidate)
  - (1 - lambda) * maxSimilarity(candidate, selected)
```

- `relevance`: 그래프 점수 + 품질 보정 점수
- `maxSimilarity`: 이미 선택된 장소와의 유사도

권장 초기값:

```text
lambda = 0.7
```

효과:

- 점수 높은 후보는 유지한다.
- 이미 선택된 장소와 지나치게 비슷한 후보는 뒤로 민다.

## 10. 6단계: 추천 사유 생성

추천 API는 결과만 반환하지 않고 추천 이유를 함께 반환해야 한다.

추천 사유 예시는 다음과 같다.

- `회원님이 저장한 장소 주변에서 반응이 높은 곳`
- `현재 위치 근처에서 최근 업로드가 많은 곳`
- `비슷한 취향의 사용자가 함께 저장한 장소`
- `최근 새롭게 주목받는 장소`

이유 생성은 내부 점수 분해 결과를 사람이 읽을 수 있는 문장으로 변환하는 역할이다.

## 11. 최종 랭킹 함수

최종 점수는 알고리즘 전체의 일부이며, 아래처럼 정리한다.

```text
rank(user, place) =
  0.55 * graphAffinity(user, place) +
  0.20 * quality(place) +
  0.15 * freshness(place) +
  0.10 * explorationBonus(place)
```

단, 이 점수식은 후보 생성과 선호 전파가 끝난 뒤의 재정렬 단계에서만 사용한다.

## 12. 콜드스타트 처리

### 12-1. 신규 사용자

- 북마크/좋아요 이력이 없으면 `graphAffinity`를 비활성화한다.
- `geo + trend + freshness` 중심으로 추천한다.
- 첫 반응 이후 seed 기반 추천으로 전환한다.

### 12-2. 신규 장소

- 등록 후 초기 기간 동안 `freshness boost`를 준다.
- 주변 사용자 추천에서 소량 탐색 슬롯으로 노출한다.
- 일정 기간 반응이 없으면 자연스럽게 보정치를 축소한다.

## 13. 구현 책임 분리 권장안

추천 로직은 기존 `PlaceQueryService`에 섞지 않는다.

권장 책임 분리는 다음과 같다.

- `PlaceRecommendationController`
  추천 API 노출
- `PlaceRecommendationQueryService`
  추천 흐름 오케스트레이션
- `PlaceRecommendationRepository`
  후보 조회, 집계 조회, 유사도 조회
- `PlaceSimilarityService`
  장소-장소 유사도 계산 또는 snapshot 사용
- `PlaceRecommendationScorer`
  그래프 전파 후 최종 점수 산정
- `PlaceRecommendationReasonFactory`
  추천 이유 생성

## 14. 단계별 도입 계획

### 14-1. 1차 MVP

- Geo Candidate 구현
- bookmark/like 기반 seed 추출
- 간단한 장소-장소 유사도 계산
- Personalized Random Walk 또는 근사 버전 적용
- 추천 사유 반환

### 14-2. 2차 안정화

- 장소 유사도 snapshot 도입
- 인기/신규/개인화 후보 비율 조정
- MMR 재정렬 도입

### 14-3. 3차 고도화

- 추천 노출 로그 저장
- 클릭/북마크 전환율 반영
- exploration 정식 적용
- learning-to-rank 실험 기반 고도화

## 15. 현재 설계의 현실적 판단

현재 프로젝트는 추천 고도화에 필요한 로그 데이터가 충분하지 않다. 따라서 지금 단계에서 가장 현실적인 접근은 다음과 같다.

- 딥러닝 기반 추천은 도입하지 않는다.
- matrix factorization 단독 적용도 아직은 과하다.
- `위치 기반 후보 생성 + 그래프 선호 전파 + 다양성 보정` 구조가 현재 데이터와 운영 복잡도에 가장 적합하다.

이 설계는 과도한 이론화보다 현재 코드베이스와 향후 확장성을 모두 고려한 실용적인 1차 추천 구조다.
