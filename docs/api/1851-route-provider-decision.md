# 경로 공급자 선택 구조 검토 (#1851)

2026-11-12 1차 검토 결정: 확정된 확장 요구가 확인될 때까지 `RouteQueryService`의 현재 분기를 유지한다.
이번 변경은 결정 기록이며 운영 코드·API·전송 설정을 변경하지 않는다.

## 확인한 범위와 근거

현재 서비스는 입력을 검증한 뒤 다음 세 클라이언트 중 하나에 위임한다.

| mode | 클라이언트 | 공개 계약 |
|---|---|---|
| car | NaverDirectionsClient | [자동차 경로](1735-car-route-api.md) |
| transit | TmapTransitClient | [대중교통 경로](1780-tmap-transit-route.md) |
| walk | TmapPedestrianClient | [보행자 경로](1795-tmap-pedestrian-route.md) |

검토한 #1851 계획과 위 API 문서에는 추가 mode의 확정 일정, 같은 mode의 복수 공급자 선택,
지역·사용자별 공급자 선택, 장애 시 fallback의 확정 요구가 없다. 이는 해당 자료에서 확인하지
못했다는 의미이며 제품의 확장 계획이 없다는 확정은 아니다. 제품 담당자의 확인은 남아 있다.

현재 서비스는 입력 검증과 세 가지 위임에 한정되어 있다. 이 상태에서 registry와 adapter 계층을
추가하면 공급자 선택 정책이 명확해지는 이익 없이 연결·등록 검증 책임만 늘어난다. 기존 구조를
유지하고 실제 요구가 확정될 때 변경 범위를 다시 정한다.

## 재검토 조건

다음 중 하나가 구체적인 요구와 적용 시점으로 확인되면 별도 설계를 진행한다.

- 새 mode 또는 새 공급자 추가
- 같은 mode에 여러 공급자를 두고 선택하는 기준
- 지역·사용자·요금·쿼터에 따른 공급자 선택
- 장애 시 다른 공급자로 전환할 조건과 응답·과금 계약

그때 필요한 범위에 한해 공급자 포트와 등록 구조를 검토한다. mode별 Map만으로 복수 공급자
선택 정책을 대체하지 않는다. 새 응답 종류는 현재 sealed `RouteResult`와 OpenAPI에도 영향을
주므로 공급자 등록만으로 API 전체가 확장된다고 가정하지 않는다.

## 후속 변경에서 보존할 계약

- 잘못된 좌표·미지 mode는 400, bike는 422이며 검증 실패 시 공급자를 호출하지 않는다.
- car/transit/walk의 공급자와 응답을 보존하며 임의 fallback을 추가하지 않는다.
- JWT·호출 제한·`Cache-Control: no-store` 및 경로 비저장 정책을 유지한다.
- 공급자별 활성화·timeout·요청 취소·자동 재시도 및 redirect 비활성화 설정은 기존 위치에 둔다.
- 키·좌표·공급자 원문 오류를 로그나 응답에 추가하지 않는다.

정적 검토는 `RouteQueryService`, `RouteResult`, `RouteController`, 세 공급자 설정 및
`RouteQueryServiceTest`의 위임·입력 거절 회귀를 대조했다. 문서만 변경하므로 테스트와 빌드는
실행하지 않았다. 공급자 구조를 변경할 때 직접 관련 단위 테스트를 실행하고 새 API 계약의
통합 검증 범위를 별도로 정한다.
