# 예약 확인 계약 (#1746)

## 적용 범위

사용자가 견적 화면을 확인한 뒤 직접 `POST /reservations`를 호출하는 계약이다. AI는 초안 준비만 수행하며 예약 생성·취소·결제 요청을 자동 실행하지 않는다. 앱의 AI 상품 지원 범위는 기존 GENERAL을 유지한다.

`confirmationToken`이 없는 기존 요청과 기존 응답 필드는 유지한다. 구버전 예약의 `confirmation`은 null이며, 해당 예약에는 새 확인 조건 보장이 적용되지 않는다. 새 확인 흐름은 토큰을 반드시 제출해야 한다. 예약 생성 성공(201, PENDING)은 관리자 확정이나 결제 성공을 의미하지 않는다.

## 가격·정책 등록

활성 점주가 본인 슬롯에 `PUT /merchant-owner/availabilities/{availabilityId}/reservation-terms`로 명시적으로 설정한다.

```json
{
  "unitAmountMinor": 1000,
  "additionalAmountMinor": 50,
  "currency": "KRW",
  "timezone": "Asia/Seoul",
  "cancellable": true,
  "cancellationCutoffMinutes": 60
}
```

예시 값은 운영 기본값이 아니다. 기존 슬롯은 미설정을 유지하고 `QUOTE_TERMS_UNAVAILABLE`로 견적 제공을 거절한다. 미설정과 명시적 무료(단가·추가 비용 모두 0), 명시적 취소 불가를 구분한다.

- 금액은 ISO 통화의 최소 단위 정수다. KRW/JPY는 1, USD/EUR는 0.01 단위이며 `currencyFractionDigits`를 제공한다. 반올림·환율 변환 없이 `단가 × 인원 + 예약당 추가 비용`을 계산하고 overflow는 거절한다.
- 총액이 양수이면 `paymentRequired=true`다. 결제는 별도의 명시적 사용자 동작이며 견적 발급에서 공급자를 호출하지 않는다.
- 지원 취소 정책은 **취소 불가**, 또는 **시작 N분 전까지 수수료 0·추가 비용을 포함한 전액 환불**이다. 부분 환불·단계별 수수료 정책은 지원하지 않으며 그런 정책을 임의로 대체하지 않는다.
- `cancellable=true`일 때 `cancellationCutoffMinutes`는 필수이며 0 이상이다. false일 때는 null이어야 한다. 취소 기한 도달 시점부터 취소할 수 없다.
- 기존 슬롯의 LocalDateTime은 기존 주입 Clock 시간대 기준으로 해석한다. 현재 기본 Clock은 UTC다. 지정 timezone은 같은 예약 순간을 표시하는 IANA 시간대이며 기존 시각을 다른 순간으로 재해석하지 않는다. offset이 포함된 시작·종료·취소 기한을 응답한다.
- 설정 변경은 조건 버전을 증가시킨다. 이미 생성된 예약에는 수락한 스냅샷이 유지된다.

## 상점주 저장 조건 조회

활성 점주는 `GET /merchant-owner/availabilities`로 본인 슬롯의 현재 편집값을 조회한다. 각 응답의
`reservationTerms`는 미설정일 때만 null이며, `0` 금액 또는 `cancellable=false`는 저장된 명시값이다.
`conditionsVersion`은 조건 변경 감지용 버전으로 항상 제공한다. 목록은 현재 소유 관계가 있는 슬롯만
반환하므로 타 점주·삭제된 소유 관계의 슬롯은 노출하지 않는다.

## 견적 준비와 최종 확인

1. 활성 일반 사용자가 `GET /places/{placeId}/availabilities/{availabilityId}/quote?quantity=2`를 호출한다.
2. 서버는 실제 장소·상품·슬롯·정원과 설정을 확인하고 사용자 소유의 불투명 `confirmationToken`, `confirmation`, `remainingCapacity`를 반환한다. GENERAL 상품 ID/이름은 null, TICKET/CLASS는 실제 상품 ID/이름이다. 미연결·비활성·타 장소·유형 불일치 상품은 제공하지 않는다.
3. 확인 화면에 대상·시간·인원·금액·통화·결제 필요 여부·취소 조건을 표시한다. 유효기간은 최대 5분이며 슬롯 시작 전에 끝난다. 견적 발급은 준비 기록만 저장하고 예약 생성·결제·재고 점유를 수행하지 않는다.
4. 최종 확인 직전에 견적을 다시 조회한다. 새 토큰의 값이 표시 값과 달라졌다면 사용자의 재확인을 받는다. 새 조건으로 자동 제출하지 않는다.
5. 사용자가 확인한 토큰을 기존 생성 본문에 `confirmationToken`으로 추가한다. 같은 트랜잭션에서 사용자 → 견적 → 슬롯 → 상품 잠금 순서로 조건을 검증하고 재고를 차감한다. 다른 예약의 단순 재고 차감은 조건 버전을 증가시키지 않는다.
6. 생성·상세 응답의 `confirmation`으로 실제 수락한 조건을 확인한다. 토큰은 하나의 예약 의도에만 사용하며 두 번째 키로 같은 토큰을 재사용할 수 없다.

## 오류와 응답 유실 복구

| HTTP / code | 의미 및 앱 처리 |
| --- | --- |
| 400 / VALIDATION_FAILED, INVALID_RESERVATION_INPUT | 입력값 수정. 예약 실행 전 검증 실패 |
| 403 / TOURIST_ACCOUNT_REQUIRED | 활성 일반 사용자 필요 |
| 404 / QUOTE_NOT_FOUND | 본인 토큰 부재. 다른 사용자 견적은 공개하지 않음 |
| 404 / RESERVATION_SLOT_NOT_FOUND | 슬롯 부재 또는 장소 불일치. 다시 탐색·확인 |
| 409 / QUOTE_REQUEST_MISMATCH | 토큰의 대상·인원과 생성 요청 불일치 |
| 409 / QUOTE_CONDITIONS_CHANGED | 상품·시간·가격·정책 조건 변경. 다시 확인 |
| 409 / RESERVATION_SLOT_INACTIVE | 슬롯 비활성 또는 시작됨. 다시 확인 |
| 409 / RESERVATION_PRODUCT_UNAVAILABLE | 상품 연결·유형·상태가 유효하지 않음 |
| 409 / RESERVATION_CAPACITY_EXCEEDED | 정원 부족. 다시 확인 |
| 410 / QUOTE_EXPIRED | 만료. 새 견적과 사용자 확인 필요 |
| 422 / QUOTE_TERMS_UNAVAILABLE | 가격·취소 조건 미설정 또는 계산 불가. 무료로 추측하지 않음 |
| 429 / QUOTE_RATE_LIMITED | 사용자당 시간당 60건 또는 미사용 견적 120건 한도 초과. 잠시 후 다시 조회 |
| 409 / IDEMPOTENCY_KEY_REUSED | 같은 사용자 키 또는 토큰을 다른 요청에 사용함 |

키 범위는 사용자별이며 성공 예약과 토큰이 사용된 거절 영수증은 자동 만료하지 않는다. 동일 본문 비교는 슬롯·인원·예약자 이름·전화·요청사항·토큰을 포함한다. 기존과 동일하게 이름·전화는 trim, 비어 있는 요청사항은 null로 정규화한다. 견적에는 예약자 개인정보 원문 대신 요청 지문만 저장한다.

응답 유실·timeout·5xx에는 **동일 키·동일 토큰·동일 본문**을 재전송한다. 같은 사용자 행 잠금으로 처리 중 요청의 완료를 기다리며, 성공이 커밋됐다면 원래 예약을 201로 반환한다. 이때 견적 만료나 이후 가격 변경은 이미 성공한 요청의 복구를 막지 않는다. 생성 전 확정한 조건 거절은 영수증을 커밋하고 같은 오류로 복구한다. 미확정 서버 오류는 예약·재고·키 바인딩을 롤백하므로 같은 의도를 재시도할 수 있다.

인증·본문 검증 실패나 본인 견적이 없는 요청은 영수증을 생성하지 않는다. 네트워크 오류만으로 실패를 확정하거나 새 키를 만들지 않는다. 확정 거절을 확인한 뒤 새 조건으로 진행하려면 새 견적·사용자 재확인·새 키가 필요하다.

발급은 사용자 행 잠금 아래 최근 1시간 60건·미사용 기록 120건으로 제한한다. 한도 초과는 슬롯 잠금과 기록 생성 전에 거절한다. 시간당 한도에는 사용된 견적도 포함하며, 미사용 한도에는 만료 후 정리를 기다리는 견적도 포함한다.

사용하지 않은 견적은 발급 24시간 후부터 1분마다 정리한다. 한 번에 최대 20개 배치(배치당 1,000건)를 처리하고 2초의 작업 예산이 지나면 추가 배치를 시작하지 않는다. 각 배치는 별도 트랜잭션으로 커밋하고 2초의 트랜잭션 timeout을 적용한다. 사용 중 행은 SKIP LOCKED로 건너뛰며, 사용된 토큰·성공 연결·거절 영수증은 보존한다. `reservation.quote.cleanup-delay-ms`의 기본값은 60,000이다.

생성 검증은 호출자의 예약 트랜잭션 안에서만 실행하며 확정 거절은 rollback-only로 표시하지 않는다. 슬롯·상품 잠금과 조건 조회를 마친 뒤 만료를 다시 검사하므로, 대기 중 만료된 견적도 `QUOTE_EXPIRED`로 거절한다.

## 결제·취소 경계

견적이 있는 유료 예약의 결제 명령에는 수락한 기대 금액·통화를 전달한다. 공급자 응답이 다르면 PAID/정산 원장으로 기록하지 않고 PROCESSING을 유지하며 `503 PAYMENT_QUOTE_MISMATCH`를 반환한다. 공급자가 이미 승인했을 수 있으므로 운영 확인과 같은 결제 키가 필요하다. 무료 예약에는 공급자 결제를 생성하지 않는다.

견적이 있는 예약의 취소는 수락한 정책과 기한을 따른다. 처리 중 결제·미환불 결제가 있으면 `409 RESERVATION_REFUND_REQUIRED`로 거절한다. 환불은 기존 명시적 환불 동작으로 먼저 완료해야 하며, 취소 요청이 자동 환불을 수행하지 않는다. 기존 예약 상태 규칙(확정 예약만 취소)을 유지한다. 일반 결제의 모든 확정·환불 불변식이나 실제 결제 공급자 구현을 이 문서가 완료했다고 의미하지 않는다.

## 검증·배포 인계

- 단위 검증: 무료/유료/미설정, 계산·timezone JSON 복원, 변경·만료·정원·상품 연결·타 사용자, 재전송·본문 충돌, 기존 터치 예약, 결제 금액/통화 비교.
- PostgreSQL 검증 대상: 같은 의도 동시 제출 시 단일 예약·단일 재고 차감, 확정 거절 커밋과 재사용, 서버 오류 시 예약·재고·영수증 롤백. 해당 테스트는 점주 자격 조회와 이벤트 발행을 격리하므로 운영 인가·outbox 성공의 증거가 아니다.
- 마이그레이션 검증 대상: V137의 nullable 초기 상태, 견적 바인딩 고유 제약, 예약의 토큰·스냅샷 쌍과 외래 키.
- OpenAPI 검증 대상: app 견적·예약 계약과 merchant 설정 계약의 소속, required/nullable, 인증·성공·오류 표현.
- 배포 이후 실제 슬롯에 명시적 조건을 설정하고 인증된 테스트 계정으로 견적·생성·복구를 검증해야 한다. 운영 예약·취소·결제의 실행은 별도 승인된 테스트 환경에서 수행한다.
- AI 세션 API는 기존 `/voice-ai/sessions` 구현을 사용한다. 배포된 AI 문서 접근 경로, 세션 생성·메시지·종료와 실제 availability 조회의 인증된 검증 결과, 배포 commit 및 URL을 인계해야 한다. JWT·예약자 개인정보는 공개 이슈나 일반 로그에 남기지 않는다.

현재 작업은 로컬 소스 변경이며 배포된 계약·인증된 운영 검증을 대체하지 않는다. 이 확인이 끝나기 전에는 #1746을 완료하거나 앱 #349의 차단이 해소됐다고 표시하지 않는다.

2026-09-30 공개 문서 재조회에서는 `/v3/api-docs/app`, `/common`, `/consulting`이 200이었으나 voice-ai path는 없었다. root `/v3/api-docs`는 내부 HTTP 8081 경로로 301이었다. 현재 확인 가능한 공개 AI OpenAPI URL은 확정하지 못했으며, 기존 프록시·AI 배포 작업과 연계해 인계해야 한다. 이 조회에서는 내부 리다이렉트를 따라가거나 인증된 mutation을 실행하지 않았다.
